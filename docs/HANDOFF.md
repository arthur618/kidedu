## 一条必须守住的纪律：验收和实现分开

现在实现者也是 Codex。同一个对话既写代码又验收自己的代码，验收就失去了意义。

- 验收必须在**新的对话**里做，不带实现时的上下文，只看分支上的代码、测试和报告。
- 做验收的对话不改被验收的代码。发现问题就写进 review，由实现的对话去改。
- 做实现的对话不改契约、不改 `scripts/`、不改 `reviews/`。
- 负责人合并分支。验收的对话不合并。

## 项目是什么

一个网页应用，帮三四年级的孩子自己完成语文作业。主线是认字（认读、理解、书写、间隔复习），副线是课外阅读和作文启发。先用一两个孩子打磨，再逐步扩大。

## 不能让步的几条

这些是产品的红线，验收时优先于“功能做完了”：

1. 孩子的照片、声音、对话、作文只发给国内模型。运行时 Agent 的 provider 必须是 deepseek，这个检查不能被绕过。OpenAI 的模型只用于不含孩子数据的离线内容生产。
2. 字词知识（读音、写法、释义、来历）只来自审过的内容库，模型不现编。
3. 不替孩子写任何可以抄进作文或作业的句子。
4. 提问时不泄露答案。
5. 孩子看到的永远是一句正常的话，不是报错。模型全部失败时流程仍能走完。
6. 仓库里不放真实孩子的数据；真实数据不贴进任何用于写代码的对话。
7. 不用连续打卡、排行榜、随机奖励这类手法留人。

## 验收的做法

我每次这样做，供你参考，可以改进：

1. 在一个和所有工作目录都无关的地方克隆主仓库，检出任务分支。
2. `npm ci`，然后 `bash scripts/verify.sh <任务号>`。自己跑，不采信报告里贴的输出。
3. 确认契约没有被改：`git diff main...HEAD -- src/contracts` 为空。
4. 把最新的 `main` 试合并进来，再跑一遍类型检查和测试。
5. 逐条核对任务文件的验收标准：有没有测试；测试是不是真的在验证这一条，而不是换了一个更容易通过的断言。
6. 读生产代码，不只读测试。重点想三件事：这段代码依赖了哪些别人没有承诺的行为；哪些输入会让孩子卡住或看到报错；红线有没有被绕开的路径。
7. 读报告的“契约问题”。实现者指出的问题大多是真的，是改进契约的主要来源。
8. 写 `reviews/<任务号>.md`（模板在 `reviews/TEMPLATE.md`），结论只有三种：通过、有条件通过、不通过。不通过时“必须修改”一节要具体到文件和行为。
9. 更新 `tasks/STATUS.md`。

到目前为止，验收发现的真问题没有一个是测试能测出来的，都是读代码时想“接起来以后会怎样”发现的：C1 的会话会卡死，D2 的红线可以被绕过，C5 的测试会连累其他分支。

## 改契约的做法

- 只加不删。确实要改已有含义时，在 `tasks/STATUS.md` 的“契约变更记录”里写明变了什么、影响哪些任务，并给受影响的任务写补充说明。
- 改完在 `main` 上跑类型检查。
- 进行中的任务不要对着移动的目标写：等它交付后一起改，再让它返工。C1 就是这样处理的。
- 契约里没写清楚的地方，实现者会按自己的理解补。验收时把这些理解收回契约，不要让它们只存在于某个实现里。
